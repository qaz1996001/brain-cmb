# RFC 2119 需求關鍵字指南 (Requirement Keywords Guide)

**文件 ID**: REG-RFC2119-001  
**標題**: RFC 2119 需求關鍵字定義與使用指南  
**版本**: v1.0.0  
**狀態**: Stable  

---

## 1. 概述 (Overview)

本指南基於 **RFC 2119** (Key words for use in RFCs to Indicate Requirement Levels)，定義了在需求文檔 (PRD, SR, SD) 中使用的核心關鍵字。這些關鍵字用於明確標註需求的強制性級別，確保人類開發者與 AI 代理能準確理解開發任務的優先級與強制性。

## 2. 關鍵字定義 (Definitions)

### 2.1 MUST / SHALL (必須)
這些單詞意味著該項定義是規格中的**絕對要求**。
- **語義**：不滿足此要求即視為不合規。
- **範例**：系統 **MUST** 在 2 秒內回應使用者請求。

### 2.2 MUST NOT / SHALL NOT (不得)
這些短語意味著該項定義是規格中的**絕對禁止**。
- **語義**：違反此禁止項即視為不合規。
- **範例**：密碼 **MUST NOT** 以明文形式儲存在資料庫中。

### 2.3 SHOULD (應該)
這個單詞意味著在某些情況下可能存在忽視該項的合理理由，但在採取不同路徑前必須充分理解並權衡潛在影響。
- **語義**：推薦做法，除非有正當理由否則應遵循。
- **範例**：系統 **SHOULD** 提供深色模式以提升使用者體驗。

### 2.4 SHOULD NOT (不應該)
這個短語意味著在某些情況下可能存在該行為是可以接受的合理理由，但在實施前必須充分理解並權衡潛在影響。
- **語義**：推薦不要這樣做，除非有正當理由。
- **範例**：API **SHOULD NOT** 返回過於詳細的錯誤堆疊資訊。

### 2.5 MAY (可以)
這個單詞意味著該項是**完全可選的**。
- **語義**：實作者可以選擇包含此項，也可以選擇不包含，均視為合規。
- **範例**：使用者 **MAY** 選擇上傳個人頭像。

## 3. 使用規則 (Usage Rules)

1. **唯一性**：每個需求敘述應僅包含一個核心關鍵字。
2. **大寫標註**：關鍵字 **MUST** 使用全大寫字母以示區別。
3. **一致性**：在同一個專案中，SHALL 與 MUST 可以互換，但建議在同一文件中保持一致。
4. **追溯性**：所有標註為 MUST 的需求 **MUST** 在測試追溯矩陣中擁有對應的驗證案例。

## 4. AI 協作建議

當 AI 代理閱讀需求時：
- 看到 **MUST**：視為開發的核心約束，不可妥協。
- 看到 **SHOULD**：如果實作成本過高或與現有架構衝突，應主動向人類開發者提出疑問並尋求確認。
- 看到 **MAY**：視為加分項或延伸功能。
